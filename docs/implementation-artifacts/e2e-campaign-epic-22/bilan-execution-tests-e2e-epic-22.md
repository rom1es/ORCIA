## 3. Regroupement synthétique des causes racines observées

### A. Cascade critique `resetDay0()` (`09_reset_db_first_boot.py`) sur FK `blackboard_snapshots -> step_executions` (`87` échecs)

- **Mécanisme exact** : dans `infra/scripts/maintenance/09_reset_db_first_boot.py`, `blackboard_snapshots` et `audit_ledger` sont déclarées dans `PROTECTED_TABLES` (protégées par trigger PostgreSQL append-only `BEFORE UPDATE OR DELETE RAISE EXCEPTION`), mais `ORDERED_MUTABLE_TABLES_TO_CLEAR` tente `DELETE FROM step_executions` et `DELETE FROM workflow_runs` sans gestion de la contrainte `blackboard_snapshots_step_execution_id_fkey` (`ON DELETE RESTRICT`).
- **Déclencheur** : dès que `#10` (`03-human-led-anchor-and-arbitration.spec.ts` `desktop-cockpit`) a persisté une exécution d'étape et son snapshot dans `blackboard_snapshots`, **tous les 87 scénarios exécutés suivants (`#11` à `#110` hors `13` skips)** ont échoué en `~1 s` dans `beforeEach` (`support/day0.ts:13`) sur `sqlalchemy.exc.IntegrityError: (sqlalchemy.dialects.postgresql.asyncpg.RestrictViolationError) update or delete on table "step_executions" violates RESTRICT setting of foreign key constraint "blackboard_snapshots_step_execution_id_fkey" on table "blackboard_snapshots"`.

### B. Rejets `HTTP 401 Unauthorized` sur les `10` premiers scénarios (`3` échecs)

- `00-stack-smoke.spec.ts` #3 (`Story 16.1`) & #4 (`Story 16.2`) (`desktop-cockpit`, `2` échecs) : les appels API directs `apiGet(request, "/api/v1/sources/inspect-lines...")` et `apiPost(request, "/api/v1/executions/reflexive")` s'exécutent juste après `resetDay0()` sans création ni authentification d'administrateur Jour 0 ; les endpoints désormais durcis retournent **HTTP 401** au lieu de `200`.
- `02-assistant-streaming-and-folders.spec.ts` #7 (`un tour d'assistant...`, `desktop-cockpit`, `1` échec) : après `configureActiveEmbeddingModelViaApi(page)` et clic sur `Envoyer à Mon Assistant`, `POST /api/v1/assistant/three-speed/stream` retourne **HTTP 401** au lieu de `< 400` (alors que les scénarios `#8` et `#9` de création/réhydratation de dossiers dans la même spec passent à `100 %`).

### C. Couverture réelle des assertions PostgreSQL 18 sur les `55` blocs `test(...)`

- **Vérifiés jusqu'au bout (`#1`–`#10`)** : `7` scénarios PASS (`users` sur `#5`/`#6`, `assistant_folders` sur `#8`/`#9`, `human_anchor_signatures` sur `#10`) et `3` scénarios FAIL sur HTTP `401` (`#3`, `#4`, `#7`).
- **Bloqués en `beforeEach` avant d'atteindre l'UI ou les assertions PG18 (`#11`–`#110`)** : `87` scénarios exécutés bloqués par `resetDay0()` + `13` scénarios ignorés par garde viewport (`test.skip`). Les assertions PostgreSQL 18 des specs `04` à `21` ainsi que de `mobile-companion` n'ont donc pas pu être exercées tant que `resetDay0()` n'est pas corrigé en Epic 23.
