# AD-23 — Journalisation 12-Factor Unifiée (JSON stdout), Puits de Logs Paramétrable (Elasticsearch/OpenSearch & Loki), Port d'Interrogation Découplé (`LogSinkQueryPort`), Traces OpenTelemetry OTLP et Conformité OpenShift [ADOPTED]

> Verbatim detail moved from `ARCHITECTURE-SPINE.md` on 2026-11-27 (baseline `bf44884`). The condensed binding form lives in the spine; this file is the full rationale.

- **Binds:** `all`, `FR-23`, `FR-24`, `FR-29`, `NFR-SEC-4`, `NFR-OBS-1`
- **Prevents:** Hétérogénéité des formats de logs entre composants (API, workers, scripts, Uvicorn, Dramatiq) ; stacktraces multi-lignes brutes non corrélées polluant la collecte de plateforme ; saturation du système de fichiers par écriture de fichiers locaux plats sans rotation ; couplage direct du code applicatif à un puits propriétaire (Elasticsearch Watcher, Loki Ruler) empêchant l'interchangeabilité d'infrastructure ; défaillance lors du déploiement en conteneur non-root sous OpenShift (SCC `restricted`, système de fichiers racine en lecture seule `readOnlyRootFilesystem: true`) ; fuite de secrets, jetons d'accès ou clés d'API dans les journaux d'infrastructure hors de l'enclave sécurisée ; et blocage de la planification de l'Epic 7 (Stories 7.2 et 7.3) faute de puits de logs interrogeable.
- **Rule:** L'architecture d'observabilité technique (logs et traces) d'ORCIA applique un principe d'**agnosticisme strict du code applicatif vis-à-vis du puits de stockage** et un respect absolu de la méthodologie **12-Factor (Logs as Event Streams)** :
  1. **Émission 12-Factor Unifiée sur `stdout` (D1, D2)** : 100 % des processus applicatifs (`api`, `worker`, `trigger-dispatcher`, scripts infra d'administration) et serveurs sous-jacents (Uvicorn, Dramatiq, DBOS, SQLAlchemy) écrivent exclusivement sur **`stdout`**, sous la règle invariante **1 ligne = 1 événement JSON sérialisé**. La standard library Python (`logging`) est unifiée via `structlog.stdlib.ProcessorFormatter`. Les exceptions et stacktraces sont systématiquement capturées et sérialisées au sein d'un attribut JSON unique `exception` (zéro ligne brute sur `stderr`). Le niveau de verbosité est piloté par la variable d'environnement **`LOG_LEVEL`** (valeurs : `DEBUG`, `INFO`, `WARNING`, `ERROR`, `CRITICAL` ; défaut : `INFO`). Les sondes de santé d'infrastructure (`/api/v1/health`, `/ready`) sont filtrées pour ne pas polluer les journaux d'accès.
  2. **Schéma Canonique Aligné ECS & Masquage Obligatoire des Secrets (D2, `NFR-SEC-4`)** : Les événements JSON respectent un schéma de champs stable et normalisé aligné sur l'Elastic Common Schema (ECS) : `timestamp` (UTC ISO-8601), `level`, `logger`, `message`, `service`, `env`, `version`, `trace_id` (W3C hex 128 bits), `span_id` (hex 64 bits), `workspace_id`, `run_id`, `step_id`. Les attributs contextuels additionnels dynamiques sont regroupés sous l'objet imbriqué `ctx` afin de bannir toute explosion de mapping dans les index du puits. Un processeur `structlog` dédié applique un **masquage systématique des secrets, mots de passe et jetons** (`SecretRef`, Bearer, PAT, mots de passe temporaires) validé en CI par le test du secret témoin (`NFR-SEC-4`).
  3. **Agnosticisme du Code & Paramétrage du Puits (D3)** : Le code applicatif ne possède aucune dépendance vers un puits de logs lors de l'émission. La collecte est entièrement déléguée à l'infrastructure d'exploitation. L'environnement d'exécution configure le comportement via deux variables d'environnement explicites : **`LOG_SINK_BACKEND=elasticsearch|loki|none`** (spécifiant le dialecte du port d'interrogation en lecture) et **`LOG_COLLECTOR=external|otel|none`** (spécifiant l'agent de collecte déployé).
  4. **Port d'Interrogation Découplé (`LogSinkQueryPort`) & Priorité Elasticsearch / OpenSearch (D4, D10)** : L'accès en lecture au puits (requis par l'auto-remédiation et les vérifications post-déploiement de l'Epic 7) est isolé derrière le port abstrait **`LogSinkQueryPort`** (`packages/orcia-core/src/orcia_core/ports/` ou `observability/ports.py`), injecté au *Composition Root* (`lifespan` FastAPI, `on_startup` worker) :
     - **Cible de Production Prioritaire (`ElasticsearchLogSinkAdapter`)** : Interroge le puits Elasticsearch / OpenSearch de la plateforme via un client compatible sans dépendance propriétaire (`opensearch-py` ou `elasticsearch-py` en dialecte compatible).
     - **Environnement de Développement Local (`LokiLogSinkAdapter`)** : Adaptateur alternatif interrogeant l'API LogQL de Loki.
     - Les adaptateurs partagent un kit de test de contrat commun (`LogSinkContractTestKit`) exécuté sous `testcontainers` pour prouver leur parfaite substituabilité.
  5. **Détection d'Anomalies (`LOG_SINK_ALERT`) Réalisée Côté ORCIA (D5)** : La logique de surveillance et de détection des erreurs n'est jamais déléguée aux moteurs d'alerting propriétaires du puits (ni Elasticsearch Watcher ni Loki Ruler). Un acteur de worker dédié interroge périodiquement `LogSinkQueryPort`, calcule en Python pur l'empreinte normalisée de l'erreur **`error_fingerprint_sha256`**, applique la déduplication et la fenêtre de cooldown temporelle (`cooldown_window_seconds`), et émet l'alerte via la table Outbox transactionnelle `domain_events_outbox`. Un mécanisme de repli supporte la réception d'un webhook d'alerte standard de plateforme normalisé par ORCIA sur `/api/v1/triggers/alerts`.
  6. **Traces Distribuées OpenTelemetry via OTLP Standard (D6)** : Les processus Python sont instrumentés avec le SDK officiel **OpenTelemetry (`opentelemetry-sdk`, `opentelemetry-exporter-otlp`)** et les instrumentations automatiques (`fastapi`, `sqlalchemy`, `httpx`). L'export des traces s'effectue au standard W3C OTLP (gRPC / HTTP) vers `OTEL_EXPORTER_OTLP_ENDPOINT` (désactivable via `OTEL_TRACES_EXPORTER=none`). Aucun exportateur OTel Logs n'est autorisé dans le code Python : la journalisation transite exclusivement par `stdout` JSON.
  7. **Quatre Invariants Impératifs de Réversibilité (D7)** :
     - *Invariant 1 (Logs)* : Émission sur `stdout` exclusivement au format 1 ligne = 1 JSON standard (zéro client propriétaire d'envoi de logs dans l'application).
     - *Invariant 2 (Traces)* : Exportation des traces distribuées exclusivement via le protocole OTLP standard W3C (`opentelemetry-exporter-otlp`).
     - *Invariant 3 (Règles Métier)* : Calcul d'empreinte SHA-256, déduplication, seuils de cooldown et masquage des secrets implémentés à 100 % dans le code ORCIA, sans aucune logique d'alerte configurée dans l'agent de collecte.
     - *Invariant 4 (Interrogation Découplée)* : Lecture et requêtage du puits de logs réalisés exclusivement via le port `LogSinkQueryPort`.
     La bascule d'infrastructure entre agents de collecte (OTel Collector $\leftrightarrow$ Vector) ou entre puits (Loki $\leftrightarrow$ Elasticsearch) est garantie en 2 à 3 jours de travail d'infrastructure sans modifier une seule ligne de code applicatif.
  8. **Cible de Déploiement OpenShift & Contrat `ClusterLogForwarder` (D8)** : En environnement cible de production, ORCIA s'exécute dans des pods conteneurisés non root (SCC `restricted`, UID arbitraire Linux, système de fichiers racine immuable `readOnlyRootFilesystem: true`, zéro fichier de log local). La collecte des logs `stdout` est assurée par le composant de plateforme OpenShift Logging (**`ClusterLogForwarder`**) vers l'instance Elasticsearch / OpenSearch mutualisée du cluster. Le contrat d'intégration négocié avec l'équipe plateforme comprend : (a) le parsing JSON natif via `structuredTypeKey`, (b) un compte de service ou clé d'API avec permissions de lecture strictement restreintes à l'index du namespace ORCIA, et (c) une politique réseau `NetworkPolicy` d'egress vers le puits et le collecteur OTel/Tempo d'entreprise. Le masquage des secrets avant sortie du conteneur est obligatoire car les logs transitent sur le réseau de la plateforme.
  9. **Environnement de Développement Local & Rotation (D9)** : Pour le développement local, une pile légère optionnelle **Loki + Grafana** (Grafana étant configuré pour pouvoir interroger aussi bien Loki qu'Elasticsearch) est fournie via les profils Docker Compose (`--profile logs-loki`, `--profile logs-elastic`). Les scripts locaux (`scripts/manage.py`) gèrent la rotation automatique des logs locaux (`RotatingFileHandler` borné à 50 Mo) ou la suppression des fichiers au profit exclusif de `stdout`.
