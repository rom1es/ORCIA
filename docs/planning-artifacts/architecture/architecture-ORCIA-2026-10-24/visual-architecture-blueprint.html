PAUSE A : WAITING_FOR_HUMAN_ARBITRATION (FR-3)

Arbitrage d'Ambiguïté (Tie-Break)

Déclenché quand l'agent identifie ≥ 2 options équivalentes non tranchées par l'Ontologie ou la KB. Génère une matrice d'options pour l'humain.

PAUSE B : WAITING_FOR_PERMISSION (FR-27)

Blocage d'Habilitation (Permission Broker)

Déclenché sur erreur 401/403 d'une URI fédérée ou droit EXECUTE manquant. Affiche la procédure IAM exacte et le bouton Rejouer l'étape.

PAUSE C : WAITING_FOR_UPSTREAM_RESOLUTION (FR-6)

Contestation Amont & Rewind

Un rôle aval (ex. Architecte en Étape 2 ou Tech Lead en Étape 3) conteste un invariant amont ou signale une doc [STALE_WARNING]. Ouvre un arbitrage tripartite.

Mécanisme d'Arbre de Snapshots lors d'un Rewind / Replay Ciblé
Append-Only (Aucune perte d'historique d'audit)

Lorsqu'une Contestation Amont à l'Étape 3 modifie le PRD (Étape 1) ou rafraîchit une spécification dans la KB, ORCIA ne supprime jamais les anciens snapshots. Il crée une nouvelle branche à partir du snapshot révisé et marque l'ancienne branche comme SUPERSEDED :

Snapshot #101 (Étape 1: PRD v1) [SUPERSEDED]
  └── Snapshot #102 (Étape 2: Archi v1) [SUPERSEDED]
        └── Snapshot #103 (Étape 3: Pause Contestation Amont / [STALE_WARNING] OpenAPI v2.1)

──► [Arbitrage Tripartite + Mise à jour KB OpenAPI v2.4 + Replay ciblé]

Snapshot #104 (Étape 1: PRD v1.1 amendé, parent=#101) [ACTIVE_HEAD]
  └── Snapshot #105 (Étape 2: Archi v1.1 re-validée par diff, parent=#104) [ACTIVE_HEAD]
        └── Snapshot #106 (Étape 3: Plan Tech généré avec OpenAPI v2.4, parent=#105) [ACTIVE_HEAD]
3. Résolution d'URI Fédérées (`db://`, `git://`, `nexus://`), Cache CAS & Permission Broker (AD-5, AD-6, OQ-1, OQ-2)
Zéro Duplication Sauvage • Reproductibilité SHA-256
1

Déclaration Pure d'URI dans le Catalogue Fédéré

Les Workflows, Agents, Skills et Gabarits référencent leurs dépendances uniquement par URI canonique : git://gitlab.corp/platform/templates/prd.md@v2.1.0, nexus://registry.corp/skills/openapi-linter@1.4.2, db://postgres-prod.corp/sales/schema_v3.

2

Sélection de l'Identité d'Exécution (Résolution OQ-1)

• Mode Passthrough (Défaut) : Le connecteur utilise le jeton OIDC délégué (OAuth2 Token Exchange RFC 8693) ou le PAT personnel chiffré AES-256-GCM de l'utilisateur courant. L'agent ne peut jamais voir plus que l'humain.
• Mode Service Principal (Gouverné) : Uniquement si l'étape du workflow a été explicitement approuvée par un Admin avec execution_identity: service_principal, le connecteur utilise une identité machine dédiée issue du coffre-fort.

3

Interception par le Permission Broker en cas de 401/403 (Résolution OQ-2)

Si le dépôt distant ou le RBAC interne refuse l'accès, le PermissionBrokerService intercepte l'erreur, consulte la KB d'Habilitations (Markdown + Frontmatter YAML) par correspondance de motif d'URI (git://gitlab.corp/platform/*), suspend l'étape en WAITING_FOR_PERMISSION et affiche dans le Dock Agent Concierge : le rôle manquant, l'équipe approbatrice, le lien direct de demande d'accès et le bouton Rejouer l'étape.

4

Épinglage `run-lock.json` et Stockage Immuable CAS (`cas/<sha256>`)

Lorsque l'accès réussit, le contenu résolu est haché en SHA-256, stocké une seule fois dans le bucket S3/MinIO sous cas/<sha256>, et consigné dans run-lock.json. Toutes les étapes suivantes et tous les Replays lisent ce contenu figé, garantissant une reproductibilité parfaite même si le dépôt Git distant est modifié 10 minutes plus tard.

4. Ontologie Dynamique à 4 Niveaux & RAG Hybride Versionné (AD-7, AD-8)
PostgreSQL 18 CTE Récursives + pgvector 0.8.7 + BM25

Hiérarchie d'Ontologie à 4 Niveaux (Résolution `4 → 3 → 2 → 1`)

Stockée dans PostgreSQL (`ontology_concepts`, `ontology_relations`, `ontology_axioms`) avec résolution d'héritage en `< 15ms` par CTE récursive :

  • Niveau 1 — Entreprise : Vocabulaire canonique global (gouverné par les Enterprise Ontology Stewards).
  • Niveau 2 — Domaine / BU : Spécialisations métiers (Finance, Supply Chain, R&D).
  • Niveau 3 — Équipe / Workspace : Termes projet partagés par une équipe.
  • Niveau 4 — Éphémère (Run) : Termes extraits à la volée pendant le Run courant (isolés jusqu'à promotion gouvernée vers N3/N2/N1).

Les 3 Rôles Actifs du Moteur d'Ontologie

  • 1. Typage du Blackboard & des Gabarits (FR-14) : Valide que les entités produites respectent les relations et cardinalités de l'Ontologie.
  • 2. Traduction de Profil Humain (FR-15) : Adapte dynamiquement les explications et le niveau d'abstraction selon le profil (Product, Architecte, Dev, Métier, Auditeur) sans altérer les concepts canoniques.
  • 3. Expansion RAG & Axiomes de Gate (FR-16, FR-18) : Enrichit les requêtes avec les synonymes/alias et vérifie la non-contradiction sémantique aux Gates.

Pipeline RAG Hybride (RRF) & Détection d'Obsolescence `[STALE_WARNING]` (FR-16, FR-17)

1. Ingestion Docling : Conversion structurée des documents (PDF, DOCX, Markdown, OpenAPI) en chunks sémantiques.
2. Double Indexation PostgreSQL : Vecteurs denses pgvector (HNSW halfvec) + index lexical plein texte tsvector (BM25) combinés par Reciprocal Rank Fusion (RRF) et filtrés par le kb_snapshot_hash de run-lock.json.
3. Garde-Fou de Fraîcheur : Si un chunk provient d'une source dont now() - updated_at > freshness_ttl_days ou si un conflit de version est détecté, le moteur attache le badge [STALE_WARNING] visible par l'agent et par l'humain.

5. Architecture Tri-Modale des Gates & Orthogonalité des Modèles (AD-9, AD-10, AD-11, OQ-3)
Zéro Auto-Validation LLM • Anti-Rubber-Stamping

Gate 1 : Déterministe (AD-9)

Budget < 5000ms • 256MB • No-Net

Exécutée en sandbox isolée (bwrap --unshare-net / Wasmtime) :

  • Validation JSON Schema / YAML / Sections Markdown
  • Présence des signatures human_authored_required
  • Vérification des axiomes de l'Ontologie
  • Analyse statique de Pattern Drift

Gate 2 : Agentique Orthogonale (AD-10)

Modèle Évaluateur ≠ Modèle Exécuteur

Orchestrée par ModelRouterService (LiteLLM) :

  • Famille de modèle différente obligatoire
  • Contexte purgé de la Chain-of-Thought de l'exécuteur
  • Contrôle Transverse d'Invariants : Vérifie l'alignement direct de l'Étape N contre l'Étape 1 (PRD/Archi)
  • Génère le score agentic_score (0..1) et le Briefing de Revue (4 blocs)

Gate 3 : Humaine Adaptative (AD-11)

Résolution OQ-3 + Découpage

3 modes de gouvernance :

  • mandatory_full : 100% revue humaine (défaut si ancre humaine)
  • risk_or_exception_based : Auto-pass si Déterministe=PASS, Score Agentique ≥ 0.85, 0 conflit ontologie et 0 [STALE_WARNING]
  • sampling : Audit humain sur 20% des runs conformes
  • Anti-Rubber-Stamping : Alerte si validation < 15s sur artefact > 1000 mots
