## 2. Detailed Findings by Question

### Question 1: 2025–2026 Production Retrospectives on Next.js App Router with a Separate Backend (FastAPI/Go/Rust) for Non-SEO B2B Dashboards
* **High-Profile Migrations Away from Next.js App Router:** In 2025–2026, multiple prominent B2B SaaS and developer-tool companies publicly documented migrating their dashboards away from Next.js App Router toward Vite-based stacks. Notably, **Plane** migrated 1,200+ files and 20,000+ lines of code from Next.js to Vite + React Router because its rich, real-time, API-driven workspace was fundamentally client-first; doing so cut local reload times from 20–30 seconds down to milliseconds `[D1-C1]`. Similarly, **Inngest** migrated its developer dashboard from Next.js App Router to a Vite + TanStack stack after dev server startup bloated to 10–12 seconds minimum, achieving an **83% reduction in local dev time** `[D1-C2]`.
* **RSC Boundary Friction & Cognitive Load:** When a separate backend (such as Python FastAPI) already owns business logic, auth, and database access, React Server Components (`"use client"` vs. `"use server"`) offer little architectural value if no BFF is desired, while introducing serialization constraints across component props and debugging friction across server/client boundaries `[D1-C2]`.
* **Caching Complexity vs. Dynamic Dashboards:** Practitioner retrospectives consistently flag Next.js's four-layer caching model (Request Memoization, Data Cache, Full Route Cache, Router Cache) as counterproductive for authenticated, real-time B2B cockpits, forcing teams to litter routes with `dynamic = 'force-dynamic'` or wrestle with stale views `[D1-C9]`.
* **Static Export (`output: 'export'`) & Dynamic Route Friction:** Using Next.js in pure SPA / static export mode disables Middleware, headers/rewrites, and server runtime features, and forces every dynamic route (`app/runs/[id]/page.tsx`) to declare `generateStaticParams` at build time—an anti-pattern for B2B dashboards where UUIDs (such as workflow runs or workspace IDs) are created dynamically at runtime `[D1-C5]`.
* **Turbopack Maturity & Memory Footprint in Next 15/16:** While Turbopack significantly narrows the HMR gap on leaf Client Components (~70ms–90ms) and excels at cold-starting massive 800+ component monorepos (~1.6s) `[D1-C3, D1-C4]`, it maintains a heavy persistent Rust incremental computation graph in RAM—resulting in substantially higher memory consumption than Vite 6—and still incurs ~450ms HMR spikes when edits cross RSC or root layout boundaries `[D1-C4]`.

### Question 2: Vite 6 + TanStack Router v1 Performance & DX for Internal Dashboards/Cockpits (2025–2026)
* **Cold Start, HMR Speed & Memory Profile:** Vite 6 boots small-to-medium apps in ~380ms and maintains a flat ~60ms–140ms HMR latency with a minimal RAM footprint because it serves native browser ESM via esbuild/SWC without tracking server/client RSC boundaries in memory `[D1-C3, D1-C4]`.
* **Production Build Times & Automatic Code Splitting:** Paired with `@tanstack/router-plugin/vite` (`autoCodeSplitting: true`), Vite 6 automatically splits route components and data loaders into lazy chunks at build time without manual `React.lazy()` wrappers, completing production builds for medium-to-large SaaS apps in **12s–18s** with a core router bundle of ~30 KB gzipped (~88 KB minified) `[D1-C8]`.
* **Dashboard-Specific DX (URL as Typed State + TanStack Query):** For complex B2B cockpits with multi-panel layouts, filters, pagination, active tabs, and trace/run inspection state in the URL, TanStack Router v1 is widely cited as the gold standard in 2025–2026 `[D1-C7]`.

### Question 3: React Router v7 (`ssr: false` SPA Mode) vs. TanStack Router v1 and Next.js SPA Mode (2025–2026)
* **React Router v7 (`ssr: false`) vs. Next.js Static Export (`output: 'export'`):** React Router v7 runs natively on Vite 6 and, when configured with `ssr: false` in `react-router.config.ts`, pre-renders only the root layout shell into a single catch-all `index.html` file `[D1-C6]`, supporting runtime dynamic parameters (`/workspaces/:wsId/runs/:runId`) natively.
* **React Router v7 (`ssr: false`) vs. TanStack Router v1:** React Router v7 added `+types/` auto-generation via `routes.ts`, which types route path params, but navigation strings (`navigate(...)`) and URL search parameters remain loosely typed or untyped compared to TanStack Router v1's strict end-to-end compile-time link and search-param validation `[D1-C7]`.

## 3. Contradictions / Divergences Between Vendor Docs and Practitioner Experience

1. **Next.js "SPA Guide" vs. Real-World Dynamic B2B Routing:** Next.js 15/16 documentation promotes `output: 'export'` with `"use client"` roots as a first-class way to build Single-Page Applications `[D1-C5]`, whereas in practice `output: 'export'` enforces build-time `generateStaticParams` for dynamic segments (`[id]`), causing immediate friction for runtime-generated entity UUIDs `[D1-C5]`.
2. **Turbopack Benchmarks vs. Monorepo Memory & RSC Boundary Reality:** While leaf client HMR is fast, Turbopack consumes substantially more RAM in monorepos to hold its incremental graph, and any edit touching layouts or RSC boundaries introduces delays compared to pure Vite 6 ESM HMR `[D1-C1, D1-C2, D1-C4]`.
3. **React Router v7 "Type Safety" vs. TanStack Router Type Safety:** React Router v7's `+types/` only covers route module props/params, whereas broken `<Link to="...">` paths and complex URL search parameter schemas are enforced at compile time by TanStack Router v1 `[D1-C7]`.
